# Spec-Driven Docs Template — Design

**Date:** 2026-07-15
**Status:** Approved design, pre-implementation
**Source:** DAC.Infomotion "Software Delivery Process" v1.1.

## Purpose

A reusable **starter repository** for spec-driven software delivery. A team clones it, runs one setup
command, and gets a standalone spec/docs repo that drives development: every non-trivial feature is
specified and reviewed before code is written. Service repos live inside it as `workspace/` checkouts
so Claude can reason across specs and code from one place.

This template is the concrete implementation of the delivery process: feature specs pass a spec-PR
gate here; code passes a code-PR gate in the service repos. ROADMAP.md is the living hub.

## Scope

- **In:** the standalone spec/docs repo, the process (L0/L1/L2 + gates), conventions, feature spec +
  optional plan layout, Claude commands/agents, pluggable issue-tracker integration, workspace
  checkouts of service repos, ROADMAP as the living hub.
- **Out (for now):** any knowledge-base rendering (Quartz), service-repo code scaffolding beyond a
  CLAUDE.md snippet, maintenance-phase specifics.

## Writing principle for all human-facing docs

Every document meant for a human reader (README, process docs, conventions, specs, ROADMAP) is
**concise and straight to the point for a technical audience — but complete.** Omit ceremony, not
substance.

## Repository structure

```
<project>-docs/                    # the standalone starter repo (this template)
├── README.md                      # what this repo is + how to use the template (concise)
├── AGENTS.md                      # cross-tool entry point; hub → process docs
├── CLAUDE.md                      # @AGENTS.md + project context (filled at init)
├── ROADMAP.md                     # living hub: features, priorities, spec + issue + tracker links
│
├── docs/
│   ├── process/                   # THE process — tool-neutral source of truth
│   │   ├── README.md              #   SDD process, L0/L1/L2, gates, flow
│   │   └── AGENTS.md              #   hard rules for agents (incl. required spec sections)
│   ├── conventions/               # project standards (starter set, teams edit)
│   │   ├── architecture.md
│   │   ├── naming.md
│   │   ├── api.md
│   │   ├── persistence.md
│   │   ├── events.md
│   │   └── testing.md
│   └── <feature-name>/            # one folder per feature
│       ├── spec.md                #   the reviewed artifact (reviewed in the PR)
│       ├── decisions.md           #   decision log: choice + rationale + rejected alternatives
│       └── plan.md                #   optional implementation plan, not reviewed
│
├── .claude/
│   ├── commands/                  # see Commands table
│   └── agents/                    # spec-review, architecture-review, contract-data-event-review
│
├── workspace/                     # gitignored — service-repo checkouts, one dir per repo
│   └── INDEX.md                   #   generated by /setup-workspace
│
├── .mcp.json                      # tracker MCP wiring (filled at init: plane/github/gitlab)
├── .env.example                   # tokens for the chosen tracker
└── .gitignore                     # ignores workspace/
```

Key decisions:
- **`docs/process/` + `docs/conventions/`** hold the process and standards at the docs-repo level.
  Markdown is the tool-neutral source of truth; `.claude/` is only the execution adapter.
  `docs/conventions/` are **cross-repo ("fullstack") standards**; they can also serve as an input for
  generating per-repo `.claude/rules` in service repos — distinct from single-repo, stack-specific
  rules (e.g. pytest, Playwright E2E) that live in each service repo.
- **`docs/<feature-name>/`** — flat feature folders: `spec.md` (reviewed), `decisions.md` (decision
  log), and optional `plan.md`. No dates in the path; review verdicts stay in the PR, not committed.
- **No `templates/` scaffolds.** Specs and plans come from Superpowers (`brainstorming` /
  `writing-plans`); the spec's required sections (business value, level, contracts, acceptance
  criteria) are enforced as hard rules in `docs/process/AGENTS.md`, which override the skills' looser
  defaults.
- **`workspace/`** — gitignored service-repo checkouts. No Quartz / knowledge base.

## Process & gates

### Change classification

| Level | When | Process |
|-------|------|---------|
| **L0 — trivial** | typo, comment, one-liner, rename with no contract impact, safe patch bump | fast lane, no spec, done directly in the service repo |
| **L1 — normal** | typical functional change; no impact on architecture/DB/API/events | spec → spec-review → (optional plan) → issues → implement → code PR review |
| **L2 — architectural/data/contract** | new bounded context; DB/API/event/contract change; tenant isolation; framework upgrade | L1 + architecture-review + contract/data/event-review before issues |

Rules: ambiguous → pick the **higher** level; the reviewer can **raise** but not lower; the fast lane
is **L0-only** and never for changes touching DB, migrations, API, events, security, tenant isolation,
or upgrades.

### Where each gate happens

- **Spec (L1/L2)** — authored here → `docs/<feature-name>/spec.md` on a branch → **spec PR**.
  `/spec-review` runs the AI subagent and posts its verdict (PASS / PASS_WITH_ISSUES / FAIL) as a
  **PR comment/review**. PL (or delegate) approves and merges. The merge *is* the gate. Nothing
  review-related is committed to the repo — the PR history is the audit trail.
- **Architecture + contract/data/event reviews (L2 only)** — same spec PR. The AI commands seed
  verdicts as PR comments; a human's `APPROVED` on the PR is the gate before issues are created.
- **Code (all implemented work)** — gated in the **service repos** by normal human PR review, not here.

### Per-feature flow

```
select feature (from ROADMAP)
  → /new-feature  → docs/<feature>/spec.md  → spec PR
  → /spec-review  → verdict on PR
  → [L2] /arch-review + /contract-data-event-review → verdicts on same PR
  → human approves + merges spec PR         ← GATE
  → /create-issues → child issues in service repos (pluggable tracker)
  → /roadmap-sync  → ROADMAP links spec + issues + tracker; manages tracker milestones/epics
  → Devs implement in workspace/<repo>, code PRs reviewed & merged
  → all child issues close → feature done → ROADMAP updated
```

Task specs / sub-tasks below the feature spec are optional and **not** reviewed. Do not apply the full
Superpowers flow to every ticket — it is overkill for simple work and wastes tokens.

### Business value in every spec

Every feature `spec.md` opens with a **Business value / Why** section — the user or business outcome the
feature delivers and how success is judged — so developers implement against intent, not just mechanics.
Superpowers has no spec template and its brainstorming self-review does not check for this, so the
requirement is a **hard rule in `docs/process/AGENTS.md`**; per Superpowers' own precedence (project
`AGENTS.md`/`CLAUDE.md` override skill defaults), `brainstorming` honors it when writing the spec, and
`/spec-review` treats a missing or vague value statement as a finding.

### Decision log per feature

Alongside the spec, each feature keeps `docs/<feature-name>/decisions.md` — a lightweight, ADR-style
running log: the decision taken, its rationale, and the alternatives rejected. It records the **why**
(durable), distinct from the spec (the **what**) and the PR history (the review audit trail). Entries
are appended as decisions land — spec authoring, spec review, implementation — so a later reader or
agent sees not just the current design but how it got there.

## Commands & agents

### Commands (`.claude/commands/`, user-invocable)

| Command | Purpose |
|---------|---------|
| `/setup-project` | One-time init. Prompt for tracker (plane/github/gitlab) + org/project ids, plus an **optional comms channel** (Slack/Discord) for notifications; write `.mcp.json` + `.env`; fill `CLAUDE.md` project context; **ingest the approved estimate** (feature/epic list, NFRs, assumptions) and seed `ROADMAP.md` from it; print next steps. |
| `/setup-workspace` | Interactive provisioning of service repos. For each repo, ask **name, type** (frontend / backend / ML / infra / …) **and language/stack**. **Create the repo on the git host if it does not exist** (seeding an initial type/stack-aware `CLAUDE.md`); clone existing repos. Clone all into `workspace/<repo>/`; regenerate `workspace/INDEX.md` (repo, type, language, branch, last-sync). |
| `/new-feature <name>` | Orchestrate `superpowers:brainstorming` → `docs/<name>/spec.md` (following the required sections in `docs/process/AGENTS.md`); seed `docs/<name>/decisions.md`; propose the L0/L1/L2 level; optionally `superpowers:writing-plans` → `plan.md`. |
| `/spec-review <name>` | Run the `spec-review` subagent (verifies the spec is complete and states clear **business value**); post verdict as a comment on the spec PR. |
| `/arch-review <name>` | L2: run the `architecture-review` subagent; post verdict to the same PR. |
| `/contract-data-event-review <name>` | L2: run the contract/data/event subagent; post verdict to the same PR. |
| `/create-issues <name>` | Turn the approved spec (+ plan) into child issues in the relevant service repos via the configured tracker; link them back to ROADMAP. |
| `/roadmap-sync` | Refresh `ROADMAP.md` issue/tracker links; manage tracker milestones/epics. |
| `/status` | Read-only dashboard: per-feature spec state, open/closed child issues, milestone progress, pulled from the tracker. |

### Agents (`.claude/agents/`, the review brains)

`spec-review`, `architecture-review`, `contract-data-event-review` — each reads `docs/process/` +
`docs/conventions/` and emits a structured verdict. They post to PRs instead of writing committed
files.

## Pluggable tracker

A single config file `.claude/tracker.json` records the **issue tracker**, the **git host** (which may
differ — Plane is issues-only, so repos still live on GitHub or GitLab), and an **optional comms
channel** (Slack/Discord) for notifications:

```json
{
  "tracker": { "platform": "plane|github|gitlab", "org": "...", "projectId": "..." },
  "gitHost": { "platform": "github|gitlab", "org": "..." },
  "comms":   { "platform": "slack|discord", "channel": "..." }
}
```

The config is summarized in the `CLAUDE.md` project-context section for human readers.
Tracker-touching commands (`/create-issues`, `/roadmap-sync`, `/status`, `/setup-project`) read
`tracker`; repo provisioning (`/setup-workspace`) reads `gitHost`. Each branches to the right MCP/CLI
adapter. Supported at launch: trackers **Plane, GitHub, GitLab**; git hosts **GitHub, GitLab**.
Adding a platform later = one new adapter section, no command rewrites.

## Init flow (`/setup-project`)

1. Prompt for tracker choice (Plane / GitHub / GitLab) + org/project identifiers, **git-host
   choice** (GitHub / GitLab) + org — may be the same as the tracker or different — and an
   **optional comms channel** (Slack / Discord) for notifications.
2. Write `.mcp.json` (enable the chosen server(s)), `.env` from `.env.example`, and
   `.claude/tracker.json`.
3. Fill `CLAUDE.md` project context (name, stack, service-repo list, tracker + git-host config).
4. **Ingest the approved estimate** and seed `ROADMAP.md` (feature/epic list with priorities, NFRs,
   documented assumptions).
5. Print next steps (`/setup-workspace`, then `/new-feature`).

## ROADMAP.md — the living hub

One row per feature. Live status is **not** duplicated here — it lives in the tracker; the `Link`
column points to the tracker item (epic/milestone) and `/status` reads progress live from there.
`/roadmap-sync` keeps `Issues`, `Milestone`, and `Link` current:

| Feature | Priority | Level | Spec | Issues | Milestone | Link |
|---------|----------|-------|------|--------|-----------|------|
| user-onboarding | P1 | L2 | [spec](docs/user-onboarding/spec.md) | tracker links | M1 | [tracker](https://tracker/…/epic) |

## Superpowers dependency

Superpowers is a documented **prerequisite** (README setup section). `/new-feature` orchestrates
`superpowers:brainstorming` (idea → spec) and `superpowers:writing-plans` (spec → plan). Our commands
stay thin wrappers that add conventions, file placement, and roadmap linking.

## Roles (from the process doc)

- **DM** (Delivery Manager) — owns ROADMAP creation, client communication, delivery sign-off.
- **PL** (Project Lead) — sets up repos and CI/CD, reviews/merges spec PRs (may delegate).
- **Dev** — implements child issues in service repos, opens code PRs.
